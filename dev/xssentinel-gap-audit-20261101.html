00 · 结论

检测引擎与工程纪律在开源 XSS 赛道处于第一梯队；真实差距不在「扫得准不准」，而在「产品化」——分发形态、社区信任信号、语言覆盖、跨平台验证、对外证据链，五条。这五条有个共同点：全部是发布前花几天就能补齐的工程动作，没有一条需要动检测判定。

反过来说：这个赛道还活着的对手其实只有两个（dalfox v3、nuclei），而 XSSentinel 在两者的自报靶场上以更严格的口径拿过更高的分——缺的不是能力，是让外部读者相信并装上来的那一层。

02 · P0 —— 发布当天用户就会撞上的

GAP 01P0

分发形态是全场最重的一条安装路径

安全从业者的默认动作是「下载即用」。本仓目前唯一入口是 git clone + 手工 venv + pip install -e .，对照组全部有一键安装。

本仓事实（2026-11-01 实测）

  • 无 PyPI 包：pypi.org/pypi/xssentinel/json → 404
  • 无 Dockerfile：全仓 find **/Dockerfile* 零匹配
  • 无 GitHub Releases：仓库页无 Releases 导航，仅 tag v1.2.0–v1.3.0；无 release/pypi/docker 发布工作流（.github/ 仅 ci.yml）
  • 要求 Python ≥ 3.10 + venv；无头确认另需 playwright install chromium（一次浏览器下载）

同类做法

  • 覆盖面：dalfox 六种安装渠道 + 静态 musl 二进制；nuclei go install + 预编译；wapiti pip install wapiti3（PyPI v3.3.2 实测）；ZAP 安装包 + Docker
  • 共同点：核心装完 零额外下载 即可跑；本仓的 L6 真浏览器确认（能力差异化点）恰恰锁在最重的可选依赖后面

影响：第一印象即摩擦。装不起来不会有第二次机会；「pip install -e .」也会把 dev 工具链一起装上（requirements.txt 现为委托行，等价 -e ".[dev,async,ast,api]"），不符合普通用户预期。

建议：GitHub Release（把 v1.3.0 tag 转成带 CHANGELOG 摘录的正式 Release）+ PyPI 发布（trusted publishing）+ Dockerfile/GHCR，合计约 2 天，不动任何检测代码。

GAP 02P0

社区信任信号为零，而安全工具的信任门槛天然最高

用户要把一个会主动发攻击载荷的工具跑在自己机器上。对照组的信任由社区规模背书；本仓目前的信号全部指向「风险」而非「可信」。

本仓事实

  • 0 star / 0 fork / 0 watcher（GitHub 页面，2026-11-01）
  • 391 commits 唯一作者名「WorkBuddy Agent」——提交历史里没有一个人类署名
  • .github/ 仅 workflows/ci.yml：无 issue 模板、无 PR 模板、无 discussions、无 FUNDING、无 dependabot
  • SECURITY.md 联系方式是 AGENTS.md 里挂着的开放项（现文件建议走 GitHub 私密安全通告，但未写死联系人与时效承诺的归属）

同类做法

  • 社区设施：dalfox 开 discussions、贡献者数十人、文档站 + 迁移指南；nuclei 284 贡献者 + 公司背书（组织 12.2k followers）+ 每版 release notes 列新贡献者
  • ZAP：858 个 open issue 的活体社区 + OWASP 治理
  • 单人仓库不是问题本身——没有向社会解释「单人 + AI 开发如何被验证」才是

影响：AI 提交历史会触发供应链审查直觉。而本仓最大的差异化资产——变异对照门禁、1:1 测试、诚实声明文化——恰恰是回答这个质疑的证据，现在埋在 AGENTS.md 里没有站到台前。

建议：开 discussions + issue/PR 模板（1 小时）；README 顶部把「质量门禁如何运作」提炼成三行对外叙事（对应 docs/ARCHITECTURE.md 已有内容）；补 SECURITY.md 联系方式（唯一待仓库归属者填的项，10 分钟）。

GAP 03P0

文档语言结构：英文用户的上手路径断在第一步

README.en.md 存在且质量不错——但它是精简版。双语首页引着英文用户进来，然后所有深度文档都是中文。

本仓事实

  • README.en.md 约 282 行，为中文版（约 1,100+ 行）的提炼版；能力清单、跑分章节内容显著缩水
  • docs/ 七份文档（QUICKSTART / ARCHITECTURE / CONTRIBUTING / ONBOARDING / OPTIMIZATION / DEPENDENCY_AUDIT / COMPETITORS）全部中文，README 首屏「第一次用？」直接指向中文 QUICKSTART
  • CHANGELOG 中文

同类做法

  • distribution：dalfox 作者韩国人，英文一手文档站（dalfox.hahwul.com）+ 参数/检测模型/输出分页文档
  • nuclei：docs.projectdiscovery.io 按协议/模板类型分页的英文文档体系
  • ZAP：zaproxy.org 全英文 + 多语言 UI

影响：安全工具的主要受众是全球的；英文用户点开 QUICKSTART 发现是中文，转化路径就断了。这直接放大 GAP 02——英文世界既装不上、也读不懂，自然不会来验证。

建议：优先翻译 QUICKSTART（本就短，一条命令路径）与安装/退出码段落；用 GitHub Pages 挂一份最小英文文档站。不必翻 OPTIMIZATION/ARCHITECTURE——那些是维护者文档。

03 · P1 —— 影响采用与可信度

GAP 04P1

CI 只在 ubuntu 上验证，而项目的病灶集中在 Windows

这是本仓最讽刺的一条：项目开发在 Windows，AGENTS.md 用整段记录 Windows 专属病理，但 6 个 CI job 全部 ubuntu-latest。

本仓事实

  • .github/workflows/ci.yml：tests / drills / min-python / benchmark-full / nightly-gate / dependency-audit —— 全部 ubuntu-latest，Python 3.11 主力 + 3.10 下限冒烟
  • AGENTS.md 记录的 Windows 专属问题：Low 强制完整性标签导致 Playwright tempfile.mkdtemp() 全挂、Windows 保留端口段教训、SO_REUSEADDR 端口假绿、loopback 劣化期测试跳过
  • pyproject classifier 声明 Operating System :: OS Independent——无 CI 证据支撑

同类做法

  • distribution：dalfox / nuclei 为 linux / macOS / Windows（含 arm64）发布预编译产物，跨平台是产品承诺而非偶然
  • ZAP：三平台官方安装包 + Docker

影响：Windows/macOS 用户踩到的坑不在门禁覆盖内——README 里那些「环境陷阱」对外部 Windows 用户同样是陷阱，只是没有门禁替他们先踩过。

建议：加一个 windows-latest smoke job（复用 min-python 的用例子集即可，约 2 小时）。不必全量——smoke 覆盖 CLI + 传输 + API 就够把「OS Independent」变成被测量的声明。

GAP 05P1

扫描速度与 nuclei 有 7 倍差距（同靶实测）

同一批 60 例目标（phase196 交叉对跑，工具版本与逐例矩阵已入库）：nuclei 49 秒完成，本仓 346 秒。

本仓数据（benchmark/results/phase196_cross_tool.md）

  • XSSentinel：346.4s，F1 0.986（14/12 预算口径）
  • nuclei v3.9.0 dast/xss：48.6s，F1 0.839 —— 约 7× 快
  • dalfox v2.13.0：1172.7s，F1 0.825 —— 本仓比它约 3.4× 快
  • README 已诚实校准：「速度不是单向优势。nuclei 用 49s 拿到 0.839，比我们先完成 7 倍」

语境

  • 换的是检测深度与判定严谨度：本仓 F1 高 0.147，且 0 误报；nuclei 是模板引擎，单请求成本天然低
  • 缓解手段已存在：--scan-policy quick、async 引擎、CSP 感知预算门控

影响：大规模 bug bounty 目标（数百端点 × 深预算）的墙钟时间。用户第一次跑大目标时，速度差距会被直接感知，而精度优势要跑完才看得到。

建议：无需掩饰——README 的校准写法是对的。可做的是用 benchmark/req_stats.py 的「请求数才是稳定度量」思路，profile 一次每请求开销，确认时间花在判定而非 IO；如果大头在判定，同步引擎的批内并发还有空间。

GAP 06P1

对外证据链有缺口：头条对比数字在仓库外不可复现

本项目对竞品最重要的主张——XSSMaze 官方靶三工具同 scorer 对跑胜出——其证据目前不随仓库分发。

本仓事实

  • Phase 342 产物（dev/_xssmaze/cross_tool_p342.*、p342_meta.json）落在 dev/_xssmaze/，被 .gitignore 第 94 行 /dev/_* 排除——外部读者无法从仓库内容复现 0.965 vs 0.853/0.836
  • OPTIMIZATION.md 的「详见 AGENTS.md 342」是死指针：AGENTS.md 已于 2026-10-31 移除过程日志，归档文件中亦无 342 条目
  • p342_meta.json 里有完整的公平性 deviation 记录（dalfox 臂 --skip-headless、记分卡复用 p341 等）——外部看不到

对比口径的代差

  • dalfox 臂用的是 v2.13.0（Go 冻结分支）；现行版本是 Rust v3.2.x（COMPETITORS.md 记录其自报 XSSMaze 97.8%，v3.2.4 于 2026-10-07 发布）
  • 本机拿不到 v3 的 release 资产（环境所限，OPTIMIZATION.md 有记录）——客观限制，但外部读者只会看到「赢了 dalfox」四个字
  • 商业工具（Burp Pro / Acunetix）从未对跑——README 已自认

影响：在 0 star 新仓库的语境下，一个无法复现的「我们赢了」比不写更伤可信度。这与项目自己的文化（「引用门禁数字必须来自自己的运行」「证据先确认归属」）直接冲突。

建议：把 p342 摘要产物（cross_tool_p342.md/json + p342_meta.json）复制进 benchmark/results/ 并解除该路径 gitignore；修 OPTIMIZATION.md 死链；在 README 对比表标注「dalfox 对比版本 v2.13.0（Go 冻结分支），v3 Rust 版未对跑」。全部约 1 小时，不动任何代码。

GAP 07P1

生态位：专精 XSS 是定位选择，但生态厚度差距是实打实的

「XSS 专精」没有问题——问题在于用户比较时的隐性权重：nuclei 卖的不只是引擎，是 362 人共建、约三周一版的模板生态与整套 CI 接入。

对照生态（research/nuclei.md，2026-11-01）

  • nuclei-templates：11,997 个模板文件、1,269 个 XSS 模板、362 贡献者，v10.4.4→v10.5.1 间约 3 周一版，单版新增模板 68–295 个、首次贡献者 11–20 人
  • 官方 nuclei-action：SARIF → GitHub code scanning 一等公民；宣称对接 Jira / Splunk / Elastic / GitLab
  • ZAP：add-on 市场 + 全漏洞类

本仓现状

  • 场景 DSL（Nuclei 风格）无社区贡献通道：语料/场景是仓库内 JSON，没有「提 PR 加场景」的 documented 流程
  • 有 SARIF 导出（2.1.0）但没有官方 GitHub Action——CI 用户要自己写 step
  • SQLi 只是错误回显快检；retireJS 覆盖 7 个库——边界清晰，但对比表上会显得薄

影响：「要不要为一个漏洞类单独装一个工具」的决策里，生态厚度是隐性分。本仓的 DSL 与 fix_advice 数据化设计本来是冲着可扩展去的，但外部看不到参与入口。

建议：发布一个官方 xssentinel-github-action（SARIF→code scanning 是现成能力，约 1 天）；在文档里写明「给 data/scenarios.example.json 提 PR」的场景贡献流程。模板生态短期追不上，不必追——把「场景可贡献」的入口打开即可。

04 · P2 —— 记账项

GAP 08P2

单人维护 + 重门禁的长期成本

391 commits 单一作者（AI 代理署名）；测试 265 文件 / 60,685 行；全量分批门禁一次 4,554 秒（约 76 分钟），skip 75 例 / 10 文件。

影响：bus factor = 1。1:1 测试比是优点，但也意味着外部贡献者的第一条 PR 要面对一个 76 分钟的全量门禁体系——分批 runner 缓解了单进程卡死，但没有降低体系重量。

建议：不必改体系。在 CONTRIBUTING/ONBOARDING 明确「分层验证」路径：quick 切片门（分钟级）→ 单文件复跑 → 全量门留给 nightly。让贡献者知道哪一层够用。

GAP 09P2

独立靶上的真实能力缺口（已自认，放进对比语境）

外部独立靶 XSSMaze（官方 runner、第三方 ground truth）上，server 群 recall 91.3–91.7%——约 8–9% 的缺口真实存在。

影响：README 已如实记录（88 FN 中主体是 query 能力缺口，另有约 35 条是官方 runner 只给 URL 的投递契约形状）。但外部读者会把它与 dalfox 自报的 97.8% 直接并读——口径不同（本仓用官方 runner + 控制例 FP 0 的更严口径），这个「口径说明」目前只在 README 的限定段落里。

建议：维持诚实口径不动。若做 GAP 06 的证据入库，把「同 scorer 三工具对跑」的表放在最前面，自报数字的口径差异就有对照了。

GAP 10P2

爬虫深度与复杂 SPA / 鉴权流（README 自认）

爬虫是 BFS 深度 2 的轻量实现；复杂 SPA / 鉴权流建议 --headless 或人工提供入口。对照 ZAP 的 spider + AJAX spider + 认证上下文体系。

影响：对真实大站的覆盖面受限。但反证同样入库：OWASP Juice Shop 20.2.0 上一条命令报出 dom_dynamic high / browser-executed，SPA hash 路由自动发现（Phase 209）是真实能力。

建议：已知限制如实即可。值得做的是把 Juice Shop 的实战结果从能力清单深处提到 README 更显眼处——「第三方真实应用上的实测」是对 GAP 02 信任问题的最好回应之一。

05 · 不算缺点的部分

以下几项在对比中容易被误读成短板，核对证据后不成立——或者说，方向相反。

a.

「检测维度不如人」——不成立。CSP nonce 泄露利用链（全部竞品零覆盖）、真浏览器执行确认（dalfox 官方文档明示自己是 "static parse of a real response, not browser execution"；有浏览器确认的 XSSer/DOMDig 无同量级工程体系）、存储型二阶自动收网、自托管 OOB——这些是 docs/COMPETITORS.md 列出的「第三档机会清单」里本仓已占据的部分。竞品对照由项目自己的竞品文档背书，且本次未发现反面证据。

b.

「测试与门禁是负担所以是缺点」——误读。变异对照（红→还原→绿）门禁、零基础 lint 门禁、「零不是通过」的 verdict 语义，在同类开源扫描器中没有第二个——15k star 的 XSStrike 连自己的 benchmark 都没有（docs/COMPETITORS.md 原话）。这是吸引严肃用户与贡献者的资产，不是负债；它只是需要在 README 前屏被看见。

c.

「对手很多所以卷不过」——不成立。赛道分层实测：dalfox v3（周更）与 nuclei 是仅有的两个活跃对手；XSStrike 半停更（2025-04 后无 push），GoSpider / XSLeaks 事实停更。活牌桌只有三人，且本仓在 XSSMaze 同 scorer 对跑中 F1 0.965 领先两者（0.853 / 0.836）。

d.

「许可证」——是优点。MIT 对商业使用比 wapiti 的 GPL-2.0 更友好；依赖面干净（核心仅 5 个直接依赖，pyproject 实测），fresh-install pip-audit 0 advisory（dependency-audit job，2026-11-01 起 blocking）。
