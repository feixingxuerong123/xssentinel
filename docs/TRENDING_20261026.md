## 2. 方向①:AI Agent 攻防编排 —— 押对了路线,但接入面是短板

本仓已把 MCP 列为差异化位置(COMPETITORS.md #5),且 Phase 322 已落地 7 工具 stdio server。
本周 ARTEX(含上游 [Autumn-27/ARTEX](https://github.com/Autumn-27/ARTEX))证明这个生态位判断正确
——它就是靠「Agent 编排 + 真实工具执行」拿下的关注度。**但对照 ARTEX 的接入方式与
DalFox v3.2.4(2026-10-07)的 MCP 扩展,本仓有四个已核实的缺口:**

### 缺口 1:stdio-only,没有远程传输(阻碍 ARTEX 类平台接入)

ARTEX 系统设置里远程 MCP 工具可选 `http`(Streamable HTTP)或 `sse`(旧版 SSE)
([README「安装」节](https://github.com/trhhubsd/ARTEX))。Claude/Cursor 类客户端同理:
平台内直接填 URL 接入的只有远程 MCP。本仓 MCP 只有 `--mcp` stdio
([xssentinel/api/mcp_server.py:1-36](../xssentinel/api/mcp_server.py) docstring、
`__main__.py:1097-1100`),而 **REST API(`--serve`)已经存在**——把同一套 7 工具挂到
Streamable HTTP 端点上,是成本最低、杠杆最大的对齐项。

### 缺口 2:只回 text content,没有 structuredContent/outputSchema

`mcp_server.py:16` 自述「`tools/call` → run the tool, return text content」。DalFox v3.2.4
新增 structured tool output(`outputSchema` / `structuredContent`)——Agent 消费结构化
findings 与消费截断文本,token 成本与解析错误率差一个量级。本仓 `_MAX_FINDINGS/_MAX_FIELD`
已经在保护 Agent 上下文窗口(`mcp_server.py:50-53`),但没有结构化通道。

### 缺口 3:tools/call 静默忽略未知参数键(会产出假"干净"结论)

`mcp_server.py:974-1017` 用 `arguments.get(...)` 逐字段取值,未知键(拼写错误、单复数混用)
静默丢弃。DalFox v3.2.4 修复记录原文:*"Tool calls accept the REST argument spellings
(`cookie`, `header`, ...) and reject unknown keys instead of silently dropping them —
previously a scan could run without its cookies and report clean"*——**Agent 传错一个键名,
本仓会回一个不带认证的"无发现"结果,Agent 把它当真**。这是语义级缺陷,不是体验问题。

### 缺口 4:无 progress 通知 / cancellation / Agent Skill

DalFox v3.2.4 同批补齐 progress notifications、cancellation、resources、prompts、completions;
ARTEX 生态有 `./skills` 目录(Agent Skill 文件),DalFox 也已带 Agent Skill。本仓均无
(grep 全仓仅 `unknown tool` 一处校验,`mcp_server.py:1019`)。长扫描对 Agent 不友好,
且没有给 Agent 的"使用说明书"文件。

## 3. 方向②:扫描器自身成为攻击面 —— DalFox v3.2.4 整个 release 的主题

DalFox v3.2.4 把「目标可控数据污染扫描器输出」当作 security issue 修(fish-safe shell
quoting、终端转义序列剥离、Markdown 单元格转义、报告 0600)。逐项核对本仓:

| 项 | 本仓状态 | 证据 |
|---|---|---|
| PoC curl shell 引用 | ✅ 已对齐 | `shlex.quote`:`poc.py:146`、`replay.py:23-36`、`cookie_xss.py:262-263`、`header_xss.py:234-235`、`error_xss.py:317`、`path_xss.py:237` |
| Markdown 转义 | ✅ 已对齐 | backtick run / code fence 处理:`report.py:783-811` |
| **终端 ANSI 转义剥离** | ❌ **缺口** | 控制台直接 print 目标可控 URL/payload:`cli_commands.py:85,198-200`、`client_layers.py:122,163,496`、`transport_layers.py:155`;`desktop/app.py:47` 注释自证 "The console renders scanner output (URLs, payloads, snippets)"。全仓 grep 无 `\x1b`/ANSI 剥离逻辑 |
| 报告文件 0600 | ⚠️ 未做 | Windows 宿主影响小,Unix 部署有效(低优先级) |
| 恶意响应资源上限 | ✅ 思路已对齐 | 镜像页哨兵 + 滚动反射比熔断(Phase 78)≈ DalFox #1464 的 deep_scan cap;lxml/BS4 的实体放大与嵌套深度上限未单独验证(未查证) |

**终端转义注入**是本项里唯一确认缺失且可直接修的:目标页返回一个带 ANSI 转义序列的
反射值,就能在操作者终端里改写已扫描出的结论行(或对 Agent 注入屏幕上下文)。
修复面窄:`print` 前过一遍 `re.sub(r'\x1b\[[0-9;?]*[ -/]*[@-~]', '', s)` 级别的剥离。

附带一个同主题的**语义级不完整点**:CSP-bypass 发现场只分析**第一条** enforcing 策略
(`scanner_layers.py:392-395` 的 `break`),而 `csp.policies()` 明明返回了全部
(`csp.py:254-268`,header+meta 双通道、enforcing/report-only 分离都是对的;verifier 的
执行门也遍历全部策略,`verifier.py:409`)。多 enforcing 策略并存时,"第一条可绕"会被报成
"CSP 可绕"。DalFox v3.2.4 的对应修法是 "CSP analysis merges every enforcing policy
(multiple headers and `<meta>`)"。另外 requests 会把**重复** CSP 头 join 成 `, ` 单串,
`csp.policies()` 按单条策略解析(`csp.py:261-268`)——误差方向保守(易判 blocked → FN 而非 FP),
是否需要拆分待实测(未查证)。

## 4. 方向③(opentrap)与④⑤:部分已覆盖或明确不追

- **opentrap(开源 Burp 替代)**:它的核心是拦截代理 + 交互式 Repeater/Intruder。本仓的
  「被动代理 `--passive` + MITM CA(Phase 44/50)+ 桌面控制台」已覆盖「流量 → 扫描」闭环;
  交互式手工测试面(Repeater/Intruder)不属于扫描器使命,**不追**。
- **php2shell 式 CVE 快速响应**(三天内三个仓库过百星):版本指纹 → 已知 CVE 的爆发性需求
  真实存在,但它是响应型工具的赛道,与「XSS 检测正确性」的护城河(XSSMaze 925/88/0、F1 0.955)
  无关。XSStrike 15.2k star 停更 18 个月(2026-10-26 实测 pushed_at=2025-04-26)说明的正是
  star 广度 ≠ 存活。**不追,继续深钻检测正确性。**
- **供应链/MCP 生态安全**:本周多次出现在 HN,但属于开发侧安全(依赖投毒、MCP 客户端
  鲁棒性),与本仓无直接交集。唯一例外是缺口 3——MCP 输入校验就是「MCP 安全」在本仓的投影。
